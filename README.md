# Crossbid

A cross-border EU tender go/no-go qualification agent for small and medium-sized businesses.

A German IT services company wants to bid for a French public contract. The tender is 190
pages of French procurement law, the buyer wants proof of things like *capacité économique et
financière*, and the company has no idea which German document answers which French
requirement. Crossbid reads the tender in its source language, extracts the requirements,
checks each one against the company's own documents, maps required proofs to their German
equivalents through the EU's eCertis database, and produces a compliance matrix with a
go/no-go recommendation — where **every cell carries a citation or is marked partially supported**.

It is **advisory only**. It never submits a bid, and a human reviews and confirms every
verdict before it is final.

## Status

**Increments 0 to 4 are complete, and Increment 5 — the submission evidence — is in
progress.** Nine migrations, seventy-one architectural decision records, 5 802 backend tests
at 100 % line and branch coverage, and a clean `make lint` across both halves. A further nine
run against a real Postgres in CI, which is where the SQL is actually executed rather than
inspected as a string. The web app has 119 unit tests and 8 browser journeys.

A bidder can sign in, describe their company, search TED and start a bid from a notice,
upload a pack that is scanned for planted instructions before anything is embedded, read
every extracted requirement with its citation and its translation, see each one checked
against their own documents, ask the tender questions and get cited answers, then review the
matrix row by row and confirm or override the verdict. An operator can see cost per bid and
per node and switch models, prompts and tools without a redeploy.

### Measured quality

Four metrics on the three golden tenders, regenerated by `make eval` into
[`backend/evaluations/REPORT.md`](backend/evaluations/REPORT.md). Every figure below comes
from a live run on 2026-09-16; the judge is `google/gemini-2.5-flash-lite`, a different
vendor from every model under test.

| | DE | FR | EN |
|---|---|---|---|
| Requirement recall (gate 0.90) | **0.831** — fails | **0.933** — passes | **0.950** — passes |
| Citation faithfulness | 1.0000 | 1.0000 | 1.0000 |
| Retrieval: context recall | 0.929 | 0.800 | 0.893 |
| Retrieval: context precision | 0.592 | 0.546 | 0.558 |

**The German tender does not meet the recall gate, and that is stated rather than hidden.**
`uv run scripts/recall.py tests/fixtures/extractions/de.live.json` reproduces 0.831 and exits
non-zero. Two things moved it from the 0.72 this section used to quote, and neither was a
change to the extractor's prompt: the run now reads the notice PDF, which carries six of the
177 scored labels and which no run had ever opened (ADR-0067), and three extraction defects
found in Increment 2 had never been re-measured because the live test could not complete a
run at all between S5.2 and S7.1 (ADR-0066).

Two caveats a reader should carry. FR and EN clear the gate against denominators of **30 and
40 labels**, where DE's is 177 — one more miss takes FR to 0.90, so those two are far noisier
than the German figure. And the retrieval answer keys are **drafts**: the answers come from
the human-verified golden labels, but the question wording has not yet been read by a person,
and `REPORT.md` prints `draft key` beside every figure that depends on it.

**Translation adequacy is not yet measured for DE and EN.** The OpenRouter key reached its
spending limit partway through the suite. The report names the gap rather than showing three
metrics where it promises four.

The **1.00** this section quoted before Increment 4 is the Increment 0 feasibility spike
measured against 21 hand-written requirements, not the verified 177-label answer key. See
[`docs/decisions.md`](docs/decisions.md) ADR-0003 for that result and its caveats,
[`docs/architecture.md`](docs/architecture.md) for the design, and
[`docs/project-plan.md`](docs/project-plan.md) for scope and build order.

## Quick start

Requirements: [Docker](https://docs.docker.com/get-docker/),
[uv](https://docs.astral.sh/uv/getting-started/installation/), Node 20+, and an
[OpenRouter API key](https://openrouter.ai/keys).

```bash
cp infra/.env.example .env      # then set OPENROUTER_API_KEY and APP_ENCRYPTION_KEY
make install                    # uv sync in backend/, npm install in frontend/
make dev                        # db + api + web in Docker
DATABASE_URL=postgresql://crossbid:crossbid@localhost:5432/crossbid make migrate
DATABASE_URL=postgresql://crossbid:crossbid@localhost:5432/crossbid make seed-dev  # prints the NEXT_PUBLIC_DEV_COMPANY_ID line to paste into .env
```

`make migrate` applies the schema in `backend/migrations/` from the host, so it needs the
Compose database's published port; the API creates LangGraph's own tables itself at startup.
To run against the hosted Supabase project instead, set `DATABASE_URL` in `.env` to its direct
connection string and run `make migrate` once with no prefix.

- Web app — http://localhost:3000
- API docs — http://localhost:8000/docs
- Health — http://localhost:8000/health

Generate `APP_ENCRYPTION_KEY` with:

```bash
python3 -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

## Layout

```
backend/     FastAPI · Python 3.12 · uv · LangGraph      — own pyproject, Dockerfile, tests
frontend/    Next.js 15 · TypeScript · Tailwind          — own package.json, Dockerfile
infra/       Docker Compose, .env.example
scripts/     gen_dependencies.py
docs/        project plan, roadmap, ADRs, design canvas, demo runbook
             (the user guide and the critique land with Increment 5)
```

The two apps are separate processes on separate origins and share nothing but the OpenAPI
contract, from which `frontend/lib/api.ts` is generated. FastAPI owns all business logic,
database access, LLM calls, and secrets; the browser never sees an API key, a database
password, or a LangGraph checkpoint.

`dependencies.txt` is a generated manifest of every third-party package in both apps. Never
edit it by hand — run `make deps` after any dependency change. `make lint` fails on drift.

## How it works

The outer graph is a **deterministic workflow** with one human interrupt:

```
parse_docs → extract_reqs → plan_checks → check_reqs → score_verdict
           → await_review [human interrupt] → apply_review → finalize
```

Eight nodes in a fixed order. No model chooses the next step, and the only branch in the whole
graph is arithmetic: `fan_out_checks` divides the requirements into lanes, or routes straight
to scoring when there are none.

The **agentic** part is inside `check_reqs`: it fans out one ReAct agent per requirement, each
free to choose among **four** tools — company document search, tender search, eCertis evidence
lookup, and currency conversion — and to decide when it has enough to answer its own row.
`ask the tender` is a second, smaller agent over three tools.
[`docs/architecture.md`](docs/architecture.md) names every node with its inputs and outputs.
The verdict itself is rules-based, not model-generated: an unmet mandatory requirement or a
live exclusion ground yields `no_go` with the gap listed; `conditional` when open items
remain, and `insufficient_evidence` when the documents do not settle enough rows to judge.

**The verdict moves between runs, and that is the point of the human interrupt.** Three runs of
the same French tender, same company, same settings returned *conditional*, *no-go*,
*conditional* — one row out of about 145 flipped, and one unsupported mandatory row is the whole
distance between those answers (ADR-0075). A single run is not evidence about a tender, which is
why a person confirms every verdict and why nothing is ever submitted on the agent's say-so. The
eCertis lookups did not vary across the three: that path has no model in it.

Data sources are public documented APIs only — TED, eCertis, and ECB rates via Frankfurter.
**Nothing is scraped.** Procurement documents live on national platforms behind portal pages,
so the bidder uploads them.

**Tender text is untrusted input, and is treated as such.** Every page enters a prompt inside a
tagged data block the document cannot close, every chunk is scanned for text addressed to the
agent before anything is embedded, and a cheap model gives a second opinion on each flag.
[`docs/prompt-injection-report.md`](docs/prompt-injection-report.md) has the design and the
numbers: all four planted instructions caught, and zero flags across 351 chunks of real tender
prose.
